# 压力测试记录

测试日期：2026-11-12。本文只记录实际跑出来的数据，以及哪些东西没有测。

## 被测对象

| | |
|---|---|
| 硬件 | M5Stack StackChan（CoreS3），ESP32-S3 rev v0.2，16 MB Flash |
| 屏幕 | ILI9342C（触摸固件 0x03 / 厂商 0x01，按原厂规则判定为 C 版），320x240 |
| 供电 | USB 供电，电池 100% |
| 固件主频 | CPU 80 MHz（PLL），屏幕 SPI 40 MHz |
| 目标帧率 | 60 fps，每帧预算 16 667 us |

**设备上当前运行的是下文的「第 3 版」**：`build/eyes.bin`，16 800 字节，
SHA-256 `0194443eb9079a01b8c6044c79db0a57db48f78faa74bea08393729affab3609`。
源码重新编译后与设备上的镜像逐字节相同（已比对）。

对应的源码是 git tag **`eyes-v3`**（`git checkout eyes-v3` 后 `python tools/fw.py build`
即可得到上面这个镜像，打 tag 前又重新编译核对过一次）。第 1、2 版早于建仓库，没有留下源码，
下文它们的数据只作对比参考。

## 指标含义

固件每 10 秒从串口打印一行统计：

```
stat: up 20.033 s, 601 frames in 10 s, work avg 5043 us, max 13258 us, late 0
```

- `frames in 10 s`：这 10 秒画了多少帧，满帧是 600 或 601。
- `work avg / max`：一帧里「算动画 + 算像素 + 发给屏幕」的耗时，平均值和最坏值。
- `late`：落后预定节拍超过一整帧的次数，也就是掉帧次数。

压测方法（`tools/stress.py`）：从串口每 1.1 秒发一次 `n`（立即切换到下一个表情），
让每个 10 秒窗口里塞进约 9 次表情过渡，包括最大的那几种眼睛；结束后发 `v`，
让固件把屏幕显存整屏读回，和它刚画的那一帧逐像素比对。

## 其他实测项

**显存逐像素校验**（固件把整屏读回再比对，读回走的是慢速位操作，与写入通路无关）：

| 版本 | 次数 | 结果 |
|---|---|---|
| 1 | 3 | 均为 0 / 76 800 不同（亮起 1733、3072、3078 像素） |
| 2 | 1 | 0 / 76 800 不同 |
| 3 | 1 | 0 / 76 800 不同 |

共 5 次，每次比对整屏，没有出现过一个错误像素。另外把显存读回成图片看过一次
（`wide` 表情），与电脑仿真的画面一致。

**固件时钟**：统计行自带固件运行时间，与电脑时钟对比 110.2 秒，固件计 110.161 秒，
比值 0.99992。误差在串口到达时间的抖动范围内，可认为一致。

**屏幕自报状态**：ID `0xe30000`，电源模式 `0x9c`（已唤醒、显示开、升压开），
MADCTL `0x08`，像素格式 `0x05`（16 位）。

**I2C 总线**：扫描到 13 个地址
`0x21 0x23 0x34 0x36 0x38 0x40 0x41 0x50 0x51 0x58 0x68 0x69 0x6f`，
电源芯片（0x34）、IO 扩展（0x58）、触摸（0x38）、身体控制器（0x6f，版本 0x41）均应答。

## 电脑端仿真（同一份核心代码）

`build/sim.exe run` 每一帧都把「增量刷新后屏幕上的内容」和「整屏从头重画」逐像素比较；
第 3 版起还多比一次「走快速区间」和「每个像素都走精确计算」。

| 源码状态 | 时长 | 帧数 | 增量 vs 整屏不同 | 快速 vs 精确不同 |
|---|---|---|---|---|
| 第 1 版 | 3600 s | 216 000 | 0 | 未设此项 |
| 第 2 版，初稿 | 1800 s | 108 000 | **1484** | 未设此项 |
| 第 2 版，修正后 | 3600 s | 216 000 | 0 | 未设此项 |
| 第 3 版，种子 4242 | 1800 s | 108 000 | 0 | 0 |
| 第 3 版，种子 7 | 1800 s | 108 000 | 0 | 0 |
| 第 3 版，种子 990001 | 1800 s | 108 000 | 0 | 0 |
| 第 3 版（清理告警后的最终源码），种子 5 | 300 s | 18 000 | 0 | 0 |

第 2 版初稿那 1484 帧是这项检查抓到的真实回归：分包以后，像素坐标的浮点累加从包的
起点开始，同一个像素在不同的包里算出来差一级灰度。肉眼看不出，但「局部重画等于整屏重画」
不再成立。改成 `q0 + k * step` 直接计算后恢复为 0。

第 3 版三次长跑的其他读数：

| 项目 | 数值 |
|---|---|
| 每帧重画像素，平均 | 4476 ~ 4568 |
| 每帧重画像素，最坏（不计开机整屏那一帧） | 15 557 ~ 15 669 |
| 眼睛活动范围 | x 49.0~266.9，y 20.4~238.9（屏幕 320x240），触边帧数 0 |
| 眼睛中心最快移动 | 8.84 px/帧 |
| 相邻两帧位移的最大变化 | 2.05 ~ 2.09 px/帧² |

**移植是否忠实于 bloub**：用 bun 直接运行 bloub 原版引擎，取 18 个表情两只眼睛的
变换矩阵、位置、尺寸，与 C 移植的输出逐项比较，36 行里最大偏差 0.005，
正好是 bloub 自己输出时保留两位小数的舍入量。

## 没有测的东西

- **冷启动**：所有测试都是烧录后热复位。拔掉 USB、关机再开机的那条路径没有跑过。
  针对冷启动改过初始化顺序（先唤醒屏幕，再等触摸芯片应答来判断屏幕型号，最多等 0.6 秒），
  但这个改动本身只在热复位下验证过。
- **长时间运行**：设备上最长连续观测约 2 分钟。小时级的稳定性只在电脑仿真里跑过。
- **肉眼观感**：流畅度、撕裂、亮度是否合适，测试时没有人看着屏幕，只有显存读回的数据。
- **电池供电**：只在 USB 供电下测过，没有测续航。
- **ILI9342E 屏**：代码里有这条分支，这台设备是 C 版，E 版的初始化序列没有机会执行。
- **最后一次优化**：第 3 版之后还试过两处小改动（用 ROM 的 `memset` 填充实心区间和清零），
  在电脑仿真跑到一半时停止，没有上设备。已从源码撤回，不在当前固件里。

## 怎么重跑

```
python tools/stress.py 75 COM6      # 压测并做一次显存校验
python tools/fw.py key v COM6 9     # 只做显存校验
python tools/fw.py sim              # 编译仿真器
build\sim.exe run 1800 "" 4242      # 仿真 30 分钟，种子 4242
bun tools/bloub_ref.ts ../bloub     # 取 bloub 原版引擎的参考值
```
